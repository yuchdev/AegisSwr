# 📑 Agentic Instructions for Prototype Deconstruction & Analysis Workflow

```
[Target Environment] : Directory named "prototype/" in the repo root (Contains WinCrashAnalyzer source)
[Orchestrator Role]  : Lead Technical Forensic Auditor
[Objective]          : Analyze, strip, and catalog monolithic prototype dependencies and domain heuristics into cross-platform specification files.
```

## 👥 1. Agent Matrix Profiles

### DependencyScout

> **Role Definition:** Expert Windows Systems Engineer and static code analyzer.
> **Task:** Scan all files within `/prototype`. Identify, isolate, and document every hardcoded Win32 API, DLL hook (`dbghelp.dll`, `ntdll.dll`), external debugger call (`cdb.exe`), Event Viewer query (`EvtQuery`), or PowerShell dependency. Map all Windows-specific Structured Exception Handling (SEH) hex codes.

### PromptExtractor

> **Role Definition:** Prompt Engineer and Heuristics Analyst.
> **Task:** Locate all LLM communication modules within `/prototype`. Extract every raw string prompt, system message, few-shot examples, and regex-based hardcoded heuristics (e.g., looking for Null pointers or stack errors) used to feed context to the prototype's LLM engine.

### TelemetryAuditor

> **Role Definition:** FinOps and LLM Context Optimization Engineer.
> **Task:** Audit how the prototype reads logs, dumps, and telemetry. Evaluate file size limitations, token consumption behaviors, and instances where repetitive background logs are passed raw into the context window. Document the token waste baseline.

---

## 🛠️ 2. Step-by-Step Execution Plan

### Step 1: Deep Static Scan of directory `prototype/`

Direct `DependencyScout` to traverse the repository. For every monolithic dependency found, generate an entry in a running memory buffer tracking:

* File path and line number of the hook.
* Exact nature of the dependency (OS API, binary CLI execution, or local dll file dependency).
* A cross-platform replacement strategy (e.g., replacing `cdb.exe` with `gdb` or `lldb` abstractions).

### Step 2: Extraction of Domain Knowledge Rules

Direct `PromptExtractor` to analyze the LLM orchestration layer of the prototype. The agent must parse the prompts and decompose them into an isolated **Domain Logic Schema**. It must separate instructions meant for system debugging from instructions meant for application logic verification.

### Step 3: Gap & Architectural Debt Quantification

Direct `TelemetryAuditor` and `DependencyScout` to collaborate on a combined risk mapping run. They must trace where the prototype fails to capture structural data (such as silent service lockups without crash logs), and identify where the single-prompt interface is susceptible to "tunnel vision" answers.

---

## 💾 3. Expected Output Deliverables

The agent run must terminate by writing exactly four structured Markdown files into an output folder named `/specs`:

1. `WIN_DEPENDENCIES.md`: Complete register of all Windows-specific code elements with cross-platform replacement strategies.
2. `PROMPT_HEURISTICS.md`: A declarative list of prompts and regex rules extracted from the prototype, sorted by target troubleshooting domain.
3. `TOKEN_WASTE_REPORT.md`: Matrix outlining token inefficiencies within the prototype and algorithmic target guidelines for the Data Adapter layer.
4. `GAP_ANALYSIS.md`: Documentation of prototype failures, including lack of discussion tracking, single-prompt blind spots, and lack of support for non-crash scenarios.
