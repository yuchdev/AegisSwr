## 🧠 1. The Orchestration Core (Reasoning Engine)

The Orchestration Core manages the state machine governing the Multi-Agent System (MAS). It handles agent turn-taking, maintains context isolation, tracks token expenditure, and computes the consensus matrix.

```
                  ┌──────────────────────────────┐
                  │      State Graph Router      │
                  └──────────────┬───────────────┘
                                 │
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ OS Kernel Agent │     │  Code Analyst   │     │  Skeptic Agent  │
└────────┬────────┘     └────────┬────────┘     └────────┬────────┘
         │                       │                       │
         └───────────────────────┼───────────────────────┘
                                 │
                                 ▼
                  ┌──────────────────────────────┐
                  │    Consensus Evaluator       │
                  └──────────────────────────────┘

```

### State Machine Architecture

The Core treats the investigation as a state graph (e.g., using a framework like LangGraph or custom Asyncio actor loops). The core state object is passed between agents and updated at each turn:

```json
{
  "incident_id": "uuidv4",
  "incident_brief": { "logs_summary": "...", "stack_trace": "...", "ui_context": "..." },
  "discussion_history": [
    { "sender": "Code Analyst", "message": "...", "timestamp": "...", "confidence": 0.40 }
  ],
  "current_turn": "Skeptic Agent",
  "consensus_metrics": { "is_converged": false, "primary_hypothesis": "None" },
  "token_tracker": { "input_tokens": 14200, "output_tokens": 1200 }
}

```

### Consensus & Termination Logic

To prevent infinite agent loops, the Core evaluates agent confidence scores at the end of every round. It applies a weighted consensus calculation:

$$CS = \frac{\sum_{i=1}^{n} (W_i \cdot S_i)}{\sum_{i=1}^{n} W_i}$$

Where $W_i$ represents the domain authority weight of Agent $i$ for the detected fault type, and $S_i$ represents the confidence score assigned by that agent.

* **Termination Condition:** If $CS \ge 0.85$ or `discussion_history.length` reaches a maximum limit of 4 rounds, the Core drops out of the loop and routes the state to the **Output Synthesizer**.

## 🖥️ 2. Server-Side CLI & Storage Backends

This layer manages data persistence, heavy debugging binary utilities, and connections to Large Language Model (LLM) clusters.

### AI API Backend (LLM Gateway)

* **Abstraction Layer:** A unified interface interacting with external foundation LLMs (OpenAI, Anthropic) or self-hosted models (DeepSeek, Mixtral via vLLM/Ollama).
* **Streaming Handler:** Supports Server-Sent Events (SSE) to forward token-by-token agent arguments back to the Core and client UI in real time.

### Debug Backend (Symbol & Execution Utilities)

* **Symbol Server Manager:** Automatically maps binary crash dumps against corporate symbol servers (`.pdb` for Windows, DWARF for Linux) to resolve cryptic memory addresses into readable function names and source code file paths.
* **CLI Execution Wrappers:** A pool of worker threads running native command-line debuggers:
* **Windows Workers:** Spawns `cdb.exe -z <dumpfile> -c "!analyze -v; q"` to extract faulting thread frames.
* **Linux Workers:** Spawns `gdb --batch -ex "bt full" -ex "thread apply all bt"` against core files.

### Storage Backend Architecture

The system utilizes a polyglot storage layer to optimize for different data lifetimes and query paths:

| Storage Engine | Data Target | Retention Policy | Purpose |
| --- | --- | --- | --- |
| **S3 / MinIO Object Storage** | Raw inputs (Gigabyte `.dmp` files, massive production text logs, PNG screenshots). | 30 Days (Auto-expire) | Input staging for the Data Adapter layer. |
| **PostgreSQL (with JSONB)** | Core State, Agentic Discussion logs, Investigator's Rationale text. | Permanent / Audit Trail | To provide engineering management with historical diagnostic records. |
| **Qdrant / Milvus (Vector DB)** | Embeddings of historical resolved incident summaries and system architectures. | Permanent | Enables agents to quickly search for past analogous failure patterns. |

## 🔌 3. Client-Facing API Layer

The API acts as an integration gateway, ensuring that external applications, CI/CD pipelines, and internal CLI tools can securely trigger the forensic pipeline.

### REST / gRPC Endpoint Specifications

#### 1. Ingest New Incident

* **Endpoint:** `POST /v1/incidents/analyze`
* **Payload Type:** `multipart/form-data`
* **Parameters:**
* `metadata`: JSON string configuring application type, suspected incident window, and repository tags.
* `logs`: Target text/log files (handled by the Data Adapter).
* `crashdump`: Optional binary file (`.dmp`, `.core`).
* `screenshot`: Optional diagnostic image file.



#### 2. Live Stream Agentic Discussion

* **Endpoint:** `GET /v1/incidents/{incident_id}/stream`
* **Protocol:** Server-Sent Events (SSE) / WebSockets
* **Payload Returns:** Live token stream from the active agent conversation room, allowing the UI to display the debate as it happens.

#### 3. Fetch Final Report

* **Endpoint:** `GET /v1/incidents/{incident_id}/report`
* **Returns:** The completed payload containing the final root cause conclusion, developer mitigation instructions, the probabilistic code fix, or a structural questionnaire if the agents require data clarification.

## 🔒 4. Secure Containers for Code Validation

When the Code Analyst Agent synthesizes a patch to solve an incident, the platform must verify that the code compiles, passes syntax checks, and avoids creating further errors. This code cannot run bare on the host server due to security risks.

```
                  ┌──────────────────────────────┐
                  │      Orchestration Core      │
                  └──────────────┬───────────────┘
                                 │ Passes Patch Code
                                 ▼
         ┌──────────────────────────────────────────────┐
         │       gVisor / Firecracker MicroVM           │
         │  (No Network Access, Read-Only Base Files)   │
         │                                              │
         │    ┌──────────────┐      ┌──────────────┐    │
         │    │ LLVM / GCC   │ ──>  │ Static AST   │    │
         │    │ Compiler     │      │ Analyzers    │    │
         │    └──────────────┘      └──────────────┘    │
         └───────────────────────┬──────────────────────┘
                                 │ Returns AST / Logs
                                 ▼
                  ┌──────────────────────────────┐
                  │      Validation Agent        │
                  └──────────────────────────────┘

```

### Sandbox Architecture

* **Technology Isolation:** Utilizes **gVisor** (a runC compatible container runtime that intercepts system calls) or **Firecracker MicroVMs** to provide strict multi-tenant barrier isolation.
* **Network Constraint:** Containers are built with a hard drop rule on all networking capabilities (`--net=none`) to completely prevent data exfiltration loops or unauthorized connections during untrusted code assessment.

### Automated Validation Flow

1. **Mount Phase:** The container boots an ephemeral environment containing the basic target toolchain images (e.g., GCC/Clang for C++, JDK for Java, Python standard build kits).
2. **Execution Phase:** The code solution payload is injected alongside a compiler call:
```bash
# Example verification execution within sandbox
g++ -fsyntax-only -std=c++20 proposed_fix.cpp 2> compiler_errors.log

```


3. **AST Evaluation:** Runs basic abstract syntax tree (AST) verifiers and linters to catch dangerous side-effects or formatting bugs.
4. **Teardown & Callback:** The execution logs and exit codes are packaged into a JSON report, returned to the Orchestration Core, and the MicroVM instance is instantly destroyed. If compilation fails, the logs are passed straight back to the Code Analyst Agent so it can refine the fix.
