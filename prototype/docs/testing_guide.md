# Testing Guide

## Overview

WinCrash Analyzer uses a **Mock-Assisted Asset** integration strategy. Because
`cdb.exe` and a live WinDbg installation are not available on CI/CD runners,
the test suite replaces external executables with `unittest.mock` while keeping
the storage and parsing layers real.

---

## 1. Running the Tests

```bash
# Install dependencies
uv sync --extra dev

# Run the full suite
uv run python -m pytest

# Run only the integration tests
uv run python -m pytest tests/test_full_pipeline_cdb.py tests/test_js_callback_integrity.py -v
```

The `pytest.ini` at the repository root enables live log output (`log_cli = true`)
so that noisy symbol-resolution warnings are visible when a test fails.

## 3. Synthetic Test Assets (`tests/assets/`)

| Asset | Description |
| --- | --- |
| `access_violation_cdb.txt` | Verbatim CDB output for a `0xc0000005` access violation. Includes C++ template symbols such as `std::vector<int>::push_back` to exercise character-escaping paths. |
| `unhandled_exception_js.json` | Structured JSON payload emitted by the WinDbg JS Data Model for an unhandled C++ exception (`0xE06D7363`). |
| `corrupt_mini.dmp` | A 512-byte file with a valid `MDMP` header signature but a noise-filled body. Used to test the "corrupt dump" error-handling path. |
| `raw_cdb_output.txt` | Baseline CDB output used by `test_cdb_engine.py` (50 `file not found` lines to validate noise reduction). |
| `mock_js_output.json` | Baseline JS JSON used by `test_server_logic.py`. |
| `expected_script_output.js` | Expected JS script generated by `JSProviderBackend._generate_js`. |
| `realistic_trace.txt` | Short realistic stack trace used by `test_ai_backends.py` truncation tests. |

## 4. Mocking Strategy

### 4.1 Adding a New AI Backend for Integration Testing

To test a new AI backend (e.g. `ClaudeBackend`) without making live API calls:

1. Create a `MagicMock` that mimics the `AIBackendBase` interface:

```python
from unittest.mock import MagicMock

mock_claude = MagicMock()
mock_claude.analyze.return_value = "## RCA\nMocked Claude diagnosis."
```

2. Inject it into `CrashOrchestrator`:

```python
orch = CrashOrchestrator(debugger=mock_debugger, ai=mock_claude, store=store)
orch.process(dump_path, sym_path)
```

3. Assert that `mock_claude.analyze` was called with the expected stack-trace
   fragment:

```python
call_arg = mock_claude.analyze.call_args[0][0]
assert "STACK_TEXT" in call_arg
```

### 4.2 Patching the CDB Subprocess

```python
from unittest.mock import MagicMock, patch

mock_result = MagicMock()
mock_result.returncode = 0
mock_result.stdout = Path("tests/assets/access_violation_cdb.txt").read_text()

with patch("subprocess.run", return_value=mock_result):
    result = backend.extract(str(dump_file), str(sym_dir))
```

### 4.3 Using `tmp_path` for Isolated Storage

Every integration test that touches the filesystem receives the built-in
`tmp_path` fixture.  This guarantees tests are hermetic and do not share state:

```python
def test_my_pipeline(tmp_path):
    db_path = str(tmp_path / "crash_reports.db")
    store = SQLiteBackend(db_path=db_path)
    ...
```

## 6. Edge-Case Coverage

| Edge Case | Test | File |
| --- | --- | --- |
