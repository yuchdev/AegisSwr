# Storage Backends

WinCrash Analyzer supports two interchangeable persistence backends that both consume the same **Universal Data Schema** (`CrashReportEntity`).

---

## Universal Data Schema

Every backend stores a dictionary with the following fields:

| Field | Type | Description |
|---|---|---|
| `report_id` | UUID string | Unique identifier generated by the Orchestrator |
| `timestamp` | ISO-8601 string | UTC time the analysis was initiated |
| `dump_path` | string | Absolute path to the source `.dmp` file |
| `exception_code` | string | NTSTATUS code, e.g. `0xc0000005` |
| `faulting_module` | string | DLL/EXE identified as the crash site |
| `raw_stack` | string | Full un-analysed stack trace text |
| `ai_analysis` | string (Markdown) | AI-generated root-cause report |
| `engine_type` | string | `"cdb"` or `"js"` |
| `ai_model` | string | AI model used, e.g. `"gemini-1.5-pro"` |

A reference example lives in `tests/assets/sample_report.json`.

---

## Filesystem Backend

**Class:** `wincrash_analyzer.backends.store.filesystem.FilesystemBackend`

Stores each record as a human-readable `.json` file in a configurable output directory.

```python
from wincrash_analyzer.backends.store.filesystem import FilesystemBackend

backend = FilesystemBackend(output_dir="/var/crash_reports")
backend.save(record)       # writes <report_id>.json
records = backend.load_all()  # returns list[dict]
```

### File naming

- If `report_id` is present it is used as the file stem.
- Otherwise a sanitized form of `dump_path`'s basename is used.
- Unsafe characters (`< > : " / \ | ? *`) are replaced with underscores.

### When to use

Ideal for single-user CLI usage and rapid prototyping where a database is not needed.

## SQLite Backend

**Class:** `wincrash_analyzer.backends.store.sqlite.SQLiteBackend`

Stores records in a local SQLite database, enabling SQL-based trend analysis across multiple crash sessions.

```python
from wincrash_analyzer.backends.store.sqlite import SQLiteBackend

backend = SQLiteBackend(db_path="crash_reports.db")
backend.save(record)
records = backend.load_all()
```

### Table schema

See `tests/assets/schema_v1.sql` for the reference DDL. In brief:

```sql
CREATE TABLE IF NOT EXISTS crash_history (
    id              TEXT PRIMARY KEY,
    timestamp       TEXT,
    dump_name       TEXT,
    exception_code  TEXT,
    faulting_module TEXT,
    stack_trace     TEXT,
    ai_rca          TEXT,
    metadata_json   TEXT
);
```

`metadata_json` stores a JSON blob containing `engine_type` and `ai_model` so the fixed schema stays flexible as new fields are added.

### Query Guide

```sql
-- Count crashes by exception code
SELECT exception_code, COUNT(*) AS total
FROM crash_history
GROUP BY exception_code
ORDER BY total DESC;

-- Find all access violations
SELECT id, timestamp, dump_name, faulting_module
FROM crash_history
WHERE exception_code = '0xc0000005';

-- Most recent 10 reports
SELECT id, timestamp, dump_name
FROM crash_history
ORDER BY timestamp DESC
LIMIT 10;
```

### Concurrency

`sqlite3.connect` is called with `timeout=30` so that concurrent CLI runs wait for an existing write transaction rather than failing immediately.

---

## Schema Evolution

To add a new column (e.g. `user_comments`) without breaking existing databases:

```sql
ALTER TABLE crash_history ADD COLUMN user_comments TEXT DEFAULT '';
```

SQLite's `ALTER TABLE … ADD COLUMN` is non-destructive and backward-compatible. Existing rows will have `NULL` (or the specified `DEFAULT`) in the new column.

For more significant restructuring, create a new table and migrate:

```sql
CREATE TABLE crash_history_v2 AS SELECT * FROM crash_history;
ALTER TABLE crash_history_v2 ADD COLUMN user_comments TEXT DEFAULT '';
-- swap tables, drop old one
```

## Selecting a Backend

Use the factory helper for runtime selection:

```python
from wincrash_analyzer.backends.store.factory import create_storage_backend

backend = create_storage_backend("sqlite")  # or "filesystem"
```

## Data Export and Migration

WinCrash Analyzer provides a built-in action to export data between different storage backends. This is useful for migrating from a filesystem-based store to a SQLite database (or vice versa).

### CLI Usage

To export records from the default filesystem store to a SQLite database:

```bash
wincrash-analyzer export --store filesystem --to-store sqlite --to-store-config my_analysis.sqlite
```

### Options

- `export`: Specifies the export operation.
- `--store {filesystem,sqlite}`: The source storage backend (default: `filesystem`).
- `--store-config {PATH}`: Path to the source store (directory for filesystem, file for sqlite).
- `--to-store {filesystem,sqlite}`: The destination storage backend (REQUIRED for export).
- `--to-store-config {PATH}`: Path to the destination store.

### How it works

The export action:
1. Initializes the source backend using `--store` and `--store-config`.
2. Initializes the destination backend using `--to-store` and `--to-store-config`.
3. Loads all records from the source using `load_all()`.
4. Saves each record into the destination using `save()`.

If a record with the same `report_id` already exists in the destination, the behavior depends on the backend (e.g., SQLite might ignore or replace based on its implementation, though typically it's an `INSERT OR REPLACE` or similar).

---

## Error Handling

Both backends raise `wincrash_analyzer.exceptions.StorageBackendError` on failure, which is a subclass of `WinCrashError`. The Orchestrator catches this to prevent data loss from masking pipeline failures.
