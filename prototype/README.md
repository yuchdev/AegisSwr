# README.md

# WinCrash AI Analyzer

The **WinCrash AI Analyzer** is a professional-grade, modular diagnostic suite designed to bridge the gap between low-level Windows memory forensics and high-level cognitive reasoning. It automates the extraction of crash data from `.dmp` files and leverages Large Language Models (LLMs) to provide definitive Root Cause Analysis (RCA).

---

## 1. Purpose and Vision

In modern software environments, analyzing native crashes (Access Violations, Stack Corruptions, etc.) requires specialized knowledge of WinDbg and x64 architecture. This tool aims to democratize that expertise by:

* **Automating Forensic Extraction**: Eliminating the manual labor of loading dumps and running verbose commands.
* **Intelligent Reasoning**: Using AI to identify "smoking guns" in complex call stacks.
* **Historical Tracking**: Building a persistent knowledge base of every crash encountered across release cycles.

---

## 2. System Architecture

The architecture is built upon a **strictly decoupled Factory-Strategy pattern**, ensuring that no single component (Debugger, AI, or Storage) is aware of the others' internal implementations.

### 2.1 Orchestration Layer (`orchestrator.py`)

The **Orchestrator** acts as the deterministic supervisor of the diagnostic transaction.

* **State Machine Management**: Transitions the session through `INITIALIZING`, `EXTRACTING`, `PARSING`, `ANALYZING`, and `STORING`.
* **RAII Resource Safety**: Uses Python context managers to ensure `cdb.exe` processes are terminated and the `windbg_server.py` socket is released even during catastrophic failures.
* **Telemetry**: Records execution time and token consumption for auditing.

### 2.2 Debugging Engine Backends (`backends/debug/`)

Responsible for "Ground Truth" extraction from memory dumps.

* **CDB Engine (`cdb.py`)**: Wraps the legacy Console Debugger to execute `.reload /f /i` and `!analyze -v` via a subprocess.
* **JS Provider (`js_provider.py`)**: A modern engine that loads a JavaScript diagnostic script into the debugger to query the **Debugger Data Model** directly (e.g., `host.currentProcess.Threads`).

### 2.3 Async Bridge (`windbg_server.py`)

A specialized HTTP sink that captures data "pushed" from the WinDbg JS engine via `ActiveXObject("MSXML2.XMLHTTP")` and places it into a thread-safe queue for the Orchestrator.

### 2.4 Cognitive Reasoning Layer (`backends/ai/`)

Transforms technical hex dumps into human-centric intelligence.

* **Gemini Backend**: Utilizes massive context windows for full-memory dumps and multi-thread analysis.
* **OpenAI Backend**: Employs gpt-5.4's logical capabilities for precise instruction-pointer (RIP) deduction.
* **Optimization**: Implements "Middle-Out" truncation to keep the most relevant stack frames while discarding redundant symbol noise.

### 2.5 Persistence Layer (`backends/store/`)

Ensures historical durability using a **Universal Data Schema**.

* **JSON Backend**: Writes individual session reports to the filesystem for rapid inspection.
* **SQLite Backend**: Maintains a relational database for cross-dump trend analysis.

---

## 3. Universal Data Schema

All backends communicate via a unified entity to ensure total interoperability:

| Field | Type | Description |
| --- | --- | --- |
| `report_id` | UUID | Unique identifier for the analysis session. |
| `timestamp` | ISO-8601 | Time the analysis was performed. |
| `exception_code` | Hex String | The NTSTATUS code (e.g., `0xc0000005`). |
| `raw_stack` | String | The full stack trace extracted by the debugger. |
| `ai_analysis` | Markdown | The final RCA generated by the AI backend. |

## 5. Workspace Setup & System Requirements

### 5.1 Requirements

* **OS**: Windows 10/11 (x64).
* **Debugger**: **Debugging Tools for Windows** (found in the Windows SDK) must be installed. Specifically, `cdb.exe` must be in the system `PATH`.
* **Python**: 3.10 or higher.

### 5.2 Installation

1. **Clone the Repo**: `git clone <repo_url>`
2. **Install Dependencies**: `pip install -r requirements.txt`.
3. **Set Environment Variables**:
* `set GEMINI_API_KEY=your_key`
* `set OPENAI_API_KEY=your_key`.


4. **Symbol Cache**: Create `C:\symbols` to improve debugger performance.

### 5.3 Usage

#### CLI
Run the CLI by pointing it to a crash dump and your local release symbol folder:

```powershell
# Using the installed entry point
wincrash-analyzer analyze --dump "C:\Crashes\UiCrash.dmp" --sym "C:\Builds\Release" --engine js --ai gemini

# Or using python module
python -m wincrash_analyzer.cli analyze --dump "C:\Crashes\UiCrash.dmp" --sym "C:\Builds\Release"
```

#### GUI
A PySide6-based graphical interface is also available for a more interactive experience.

**Prerequisites:**
- Ensure `PySide6` is installed (`pip install -r requirements.txt`).
- A display environment (Windows Desktop).

**Starting the GUI:**
```powershell
# Using the installed entry point
wincrash-analyzer-gui

# Or using python module
python -m wincrash_analyzer.gui.app
```

The GUI allows you to:
- **Analyze**: Configure dump paths, symbols, and AI backends via a dynamic form.
- **Export**: Migrate your analysis history between storage backends (e.g., File System to SQLite).
- **Auto-Save**: Settings are persisted to `.crash_analyzer_config.json` immediately when an action is triggered, sharing state with the CLI.
